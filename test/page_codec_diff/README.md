# Page codec differential

This suite compares the production C++ page views and host-only legacy serializers
with the allocation-free Rust page model. The views use the Rust decoder; the frozen
page archives and pre-integration executable provide the independent C++ baseline.
The only storage replacement is
an in-memory `HalFile`. Rendering uses the existing section-oracle stub; this is
a page data/codec test, not a pixel or font-metric oracle.

```sh
cmake -S test -B build/test
cmake --build build/test --target PageCodecDiff SectionGoldenDump -j 6
ctest --test-dir build/test -R '^PageCodecDiff$' --output-on-failure
```

The default input is the existing frozen section archive: every page in all 312
public sections, covering three layout settings. It is not regenerated by this
test. To test freshly built sections from every public EPUB:

```sh
python3 test/page_codec_diff/run.py \
  --dump build/test/page_codec_diff/PageCodecDiff \
  --section-dump build/test/section_golden/SectionGoldenDump \
  --output /tmp/page-codec-public
```

Repeat `--epub /absolute/book.epub` to select external books. Private inputs,
section archives, page bytes and results must stay outside the repository.
`--archive` accepts an existing section archive. `--output` retains page bytes,
section/page inventory, a JSON case summary and per-page memory CSV.

Every accepted input is compared through all word accessors, cached block-style
fields, ruby strings, image fields, positions, tags, drop-cap text, footnotes,
links and image bounds. The complete C++ reserialization is compared with Rust,
including fields hidden behind C++ private members. For pristine pages, a second
comparison rebuilds the page with `xp_page_builder_*` and requires identical
bytes. A C++-generated synthetic page adds all five element tags, Korean words,
ruby, focus arrays, source ranges, inline fonts, small caps, discretionary
hyphens, negative coordinates, borders, a footnote and a link.

Mutations cover every truncation, two bit flips per byte, and 16-/32-bit field
writes at every byte position for the synthetic page and first eight fixture
pages. Values include 0, 1, both sides of the footnote/link/word limits, 65535,
INT32_MAX, 0x80000000 and UINT32_MAX. Both codecs receive the same bounded byte
input. Accepted mutations also undergo accessor and canonical-byte comparisons.
The sampler is intentionally deterministic; it does not claim exhaustive fuzzing.

The memory CSV records intercepted C++ `new`/`new[]` requests during page load,
peak requested live bytes, resident allocations/bytes, and request-size counts.
Resident bytes comprise the Page header, Rust arena, alignment padding, and
resolved C++ descriptors in one allocation. No loaded element,
line, image, vector or string owns another allocation. These are host ABI sizes
without allocator overhead, not ESP32 heap measurements. The Rust arena size is
independent of pointer width; C++ descriptor size is not.
The first row is synthetic; remaining rows match `inventory.json` in order.

## Arena and builder contract

`xp_page_arena_size` validates a complete page prefix and reports the consumed
input length and exact arena capacity. `xp_page_decode` initializes one disjoint
caller-owned buffer; failure from short input, invalid data or short capacity
leaves that buffer unchanged. Neither operation allocates. The arena is a
32-byte header, 16 bytes per element, four bytes per word on lines with any
nonempty ruby, NUL-terminated copies of ruby strings and image paths, and the
consumed page bytes. Normal lines need no ruby index. Terminated strings use a
four-byte length plus their bytes and one NUL, including empty entries on ruby
lines and empty image paths. The copies let C++ rendering borrow C strings
without making per-word or per-image allocations.
All internal references are 32-bit offsets. Byte loads permit arbitrary arena
alignment on both host and RISC-V. The caller owns and releases the buffer;
returned spans remain valid only while that buffer is unchanged and live.

`xp_page_decode` borrows a disjoint input. The file loader instead sizes through
`xp_page_probe`, reads into the final byte region, then calls
`xp_page_decode_in_place`. The probe is a sizing pass, not validation; direct
decode validates before writing the separate index. Both forms allocate nothing.
The Page header and compact render descriptors share the caller allocation.
Limits remain 10,000 words per line, 16-bit text size, 16 footnotes and 32 links;
these limits do not promise every accepted page fits the C3.

The byte arena is an internal representation, not a new disk format. Its header
is not a public serialization ABI; use queries rather than reading its fields.
Only arenas from successful decode may be queried, and their bytes must not be
modified by callers. Element and word queries use indexes, without searching
previous elements or words. Ruby lookup is constant time when present.

`xp_page_builder_init` borrows a caller-owned byte output. Append elements,
then footnotes, then links, and finish. A failed append preserves existing
records and the cursor. Capacity failure requires rebuilding into a larger
buffer; the module never grows it. `xp_page_builder_line` accepts the existing
`XpParaLine`, so P2b does not need another per-word ABI. It copies the same
NUL-terminated word prefixes as the current TextBlock constructor. All typed
input arrays require natural alignment, and all inputs must be disjoint from
the state/output. No input pointer survives an append. Finish yields wire
bytes; a caller needing resident query records sizes and decodes those bytes.

Layout-only link spans stay in the chapter builder until placement produces page
links. The unused arena attachment/query API and its index slots were removed.

No stricter content rejection is introduced. A supplied input may contain a
following page or LUT: `consumed` ends at the decoded page, matching C++.
The API rejects lengths exceeding UINT32_MAX/PTRDIFF_MAX and checked arithmetic
overflow; these cannot denote an addressable C3 page buffer. Noncanonical input
follows C++ normalization: Boolean fields become 0/1, fixed strings get a final
NUL, and drop-cap reserialization stops at its first NUL. Ruby/image strings
remain byte strings and do not require valid UTF-8. A drop cap whose first byte
is NUL is accepted by both readers but reserializes with a zero text length,
which both readers reject on a subsequent load; this existing behavior is
preserved rather than silently repaired.
